# Discovery workflow

## Stage 1 — Understand the ask

Capture:

- Raw request (verbatim gist)
- Suspected goal vs requested mechanism
- What already exists in the product
- Impact if unsolved
- Known facts vs open uncertainties

Output a short **current understanding** before deep tools.

## Stage 2 — Discover (problems first)

Prefer, **only if installed**, then fall back:

1. `grilling` (paced) → else [interview-methods.md](interview-methods.md)
2. `interview-script` if designing external user interviews → else draft a short script yourself
3. `define-jtbd-canvas` / `job-stories` → else a short job narrative in the decision log
4. `opportunity-solution-tree` → else keep opportunities ≠ features explicitly in notes
5. Assumption / hypothesis skills when risk is high → else label assumptions in the decision log
6. `competitor-analysis` mainly on L3 → else a short differentiation note

Stop when you can name the real job, pain, and success signal — not when you have a feature list.

## Stage 3 — Problem statement

Use `define-problem-statement` **if installed**, else [templates/problem-statement.md](../templates/problem-statement.md).

Problem must be solution-agnostic enough that multiple product approaches remain possible.

## Anti-patterns

- Jumping to screens/PRD in the first reply for L2/L3
- Treating the user's implementation idea as the requirement
- Asking what the codebase already answers
- Infinite interview with no decision log progress
- Claiming optional discovery skills ran when they are not installed
